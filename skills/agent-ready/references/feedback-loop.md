# 经验回流

仓库和 Agent 是一个闭环。仓库给 Agent 术语、指针、验证和护栏；Agent 的失误、评审意见和卡住的地方，再反过来改进仓库。T3 Code 的多数代码由 Agent 写成，它的指令文件、lint 规则和评测，几乎每一条都能追溯到一次真实的失误。闭环转得越顺，同类错误出现得越少，常驻指令也越短。

## 落在哪一层

一条经验要落在最便宜、又确实能拦住它的那一层：

| 层 | 适合什么样的经验 | 例子 |
|---|---|---|
| 类型 / 契约 | 结构错误：字段缺失、状态组合非法 | 接口字段用 schema 定义，服务端和各客户端跟随生成 |
| lint 规则 | 固定的语法模式、禁用的 API、导入方式、文件位置 | 测试里禁止用挂钟时间；`useEffect` 必须写明同步原因 |
| 测试 | 行为回归 | 修复缺陷时，加一个在主分支上失败的用例 |
| 检查命令 / 钩子 / CI | 流程性的遗漏 | 提交前跑格式化和 lint；常驻上下文变大时 CI 失败 |
| 评审规则 | 需要判断的规则：跨文件一致性、是否符合周边风格 | “行为变了，同一个 diff 里同步更新契约文档” |
| 指令文件 | 每次都可能碰到、又无法检查的事 | 高危操作；改动影响面清单 |
| 文档 | 只在部分任务中需要的约束和理由 | 某个子系统的设计决策 |
| 评测 | 模型面对文本时的行为 | 工具描述改写后，模型还能不能选对工具 |

越靠上越可靠：lint 每次都会执行，而一句叮嘱可能被忽略。经验落在下层（指令文件或文档）时，先问它能不能上移。

## 机械规则写成检查

- 能用固定模式识别的违规，就写成项目 linter 的自定义规则，或者钩子、CI 任务；哪种在项目里最便宜就用哪种。这比在文档里写一条规则更可靠。
- 规则的报错信息要当作给 Agent 的指令来写，参见 [文风](style.md#报错与-lint-消息)。
- 每条自定义规则配一个测试，用真实 linter 跑合规和违规两组样例。
- 绕过检查必须写理由（`-- reason`），并开启“未使用的禁用指令报错”。在评审中，凡是新增或放宽绕过检查的 PR，都不能自动批准。
- 按路径区分的规则，用 lint 的路径覆盖配置实现，每条覆盖写一行原因。
- 测试的确定性规则（无超时参数、无挂钟时间、无轮询、跳过必须带追踪编号）全部写成 lint。T3 Code 有一组这样的规则。

## 一份标准，多方读取

- 编码标准、测试规则写成一份文档。作者 Agent 通过指令文件里的指针读它，评审机器人通过路径映射读它（如 CodeRabbit 的 `path_instructions`、Macroscope 的检查定义），人工评审也读它。
- 如果同一规则必须在两处出现，两处都写“两处同时修改”。
- 评审规则限定范围：“只审本次改动的行”“只要求更少或更小的测试，不要求更多覆盖”，没有问题时只输出一个固定短语。范围不清的评审机器人会制造噪音，Agent 会被噪音带偏。
- 实现阶段的 Agent 上下文压力最大，评审阶段只看 diff。所以需要判断的标准交给评审执行，不要全塞进实现阶段的常驻指令。

## 面向模型的文本按代码对待

提示词、工具描述与参数 schema、生成标题的指令、评审机器人的提示词，都会改变模型的行为，单元测试却测不出来。

- 改这类文本前，先跑现有评测；修复模型行为问题时，先加一个在旧文本上失败的用例。
- 用例来自真实的糟糕体验，或用来守护一个真实的良好体验，并注明出处。
- 评测直接从源码导入被测文本，不复制。
- 按多次采样的多数结果判断，并加入对照用例。
- 评测要调用付费模型，所以 CI 只跑评分逻辑的单元测试。
- 规模小的项目不必建评测框架：保留几个真实的输入，修改前后各跑一次并对比，也算数。

## 收集经验

- 会话结束后复盘：Agent 在哪里花了太久找信息（缺指针）？犯了什么本可被检查拦住的错（缺检查）？评审发现了哪些作者 Agent 漏掉的问题（标准没写或没人读）？哪次工具调用特别昂贵（工具效率）？缺了哪项关键信息（访问权限）？`retro` 已安装时用它复盘，改进项按上表决定落在哪一层。
- 评审中同一类意见出现第二次时，就把它写成规则或检查。
- 规则写成后，检查它有没有替代掉旧的叮嘱，有就删掉旧的。常驻指令的修剪和预算见 [篇幅与预算](instructions.md#篇幅与预算)。
