# 冗余测试清理

全面扫描测试套件，找出没有信号的测试并安全删除。这是一次性的大范围改动，方法来自 T3 Code 的一次清理：25,928 个测试删掉约 11,000 个，456 个文件整体删除，1,195 个文件瘦身，测试文件总耗时从 1,205 秒降到 490 秒，产品行为没有变化。

目标是信号，不是覆盖率数字。保留下来的每个测试，都要能在真实回归时变红；删掉的每个测试，都要说得出属于哪一类、它独有的断言去了哪里。

## 0. 确认范围

- 默认只出报告，不删除任何测试。用户明确要求删除时，才在报告审阅后进入第 5 步。
- 确认范围：整个仓库，还是某个包或目录；是否允许修改生产代码中只被测试使用的导出。
- 删除在独立分支或工作区上进行，按包或目录分批提交。

## 1. 记录基线

- 用项目自己的测试命令，保留它的并行设置；再用运行器的机器可读报告（例如 vitest JSON reporter、`pytest --junitxml` 加 `--durations`、JUnit XML）按包记录测试数和耗时，并列出最慢的文件。
- 墙钟时间单独记录。各文件耗时之和不等于墙钟；有些报告的文件耗时不包含导入和转换的时间。
- 记录主分支上已有的失败，以及 CI 历史中的偶发失败；拿不到 CI 历史时，写明“未取得”。清理后仍然失败的测试，和基线对比后才能判断是不是清理造成的。
- 固定机器、命令和并行数，清理前后各跑一次，保证可比。

## 2. 评分标准

项目已有测试文档时，以它为准，下面只补它没有覆盖的部分。删除模式下，把补充内容和删除一起提交进项目的测试文档；只出报告时，把建议的补充写进报告。删除的类别与 [测试](testing.md#写什么) 中“不测这些”一致，下面给出逐项的判定细则。

**删除**（类别名在记录中原样使用）：

- **类型已保证**：编译器、类型检查或 schema 已经保证的形状和取值。
- **琐碎逻辑**：getter、单行透传，以及没有业务含义的常量映射。如果映射背后有写明的不变量（例如“避免误报成功”），归入保留。
- **文案**：标签、提示语，或给每个 `switch` 分支逐一写的断言。
- **冒烟**：“能渲染”“能导入”“不抛异常”。
- **mock 镜像**：断言 mock 被调用时的参数，而这些参数只是复述实现。
- **框架基础行为**：只断言 prop 被渲染出来、事件触发了传入的回调，中间没有项目自己的逻辑。
- **依赖时间的时序**：被测行为本可以用确定性时钟或事件验证，测试却靠真实时间流逝或 `sleep` 时长来断言。如果真实时长、进程恢复本身就是被测行为，归入保留。
- **挂钟性能断言**：“耗时少于 N 毫秒”。能改写成计数断言（扫描次数、调用次数）的，改写为“修剪”。
- **重复的表格行**：对被测代码做任何一处单点改动，这一行总和另一行同时变红、同时变绿。只是走同一条分支还不够：同一个清单或字符类里的不同成员，往往是各自独立的故障路径。
- **多层重复**：同一个场景在包装层、各个调用点或多端副本中各测一遍。删除高层前，先确认低层用例覆盖了同一故障路径；没有覆盖时，先把场景下沉到低层，再删高层。

**保留**：编排与状态流转、协议和格式转换、鉴权与权限边界（包括过期、轮换、权限收窄）、持久化与迁移、外部格式解析、确定性的竞态修复、带缺陷编号的回归测试、为依赖升级或打过补丁的依赖设立的守护测试、项目明文记录的性能守护，以及项目文档、契约、ADR 或源码注释中写明的不变量。保留类别写成“项目不变量：<名称>”或上面的类别名。

判断依据：文字相似、数量多、耗时长，都不能单独证明重复。用确定性时钟验证过期、轮换逻辑的测试，属于保留，不属于“依赖时间的时序”。T3 Code 的第一轮评审就把 22 个这样的鉴权测试误删了，后来在人工审阅中恢复。

## 3. 逐个评审

- 一次评审一个测试文件，需要时连同被测源码和相邻层的测试一起读。每个测试给出以下判断之一：
  - **删除**；
  - **保留**；
  - **修剪**：只删除其中冗余的断言，或把挂钟断言改写成计数断言；
  - **并入**：合并进已有用例或表格；
  - **下沉**：移到更低的层，例如浏览器测试改成单元测试，组件测试改成纯函数测试；
  - **争议**。
- 记录写成机器可读的格式，例如每行一条 JSON。字段包括：
  - 运行器报告中的完整测试名（`it.each` 每行单独一条，以运行器报告为准）；
  - 文件、判断、类别、一行理由；
  - 独有断言的去向（已由某个测试覆盖 / 并入某处 / 无独有断言）。

  记录放在工作区之外，不提交。
- 测试文件多时，可以分发给子 Agent 并行评审，用便宜的模型，每个子 Agent 拿到同一份标准和一个文件。先估算花费并征得用户同意。
- **独立两轮**：对“保留”类所在的高风险区域，跑两轮互不知情的评审，两轮都判“删除”才删；意见不一致时，由第三票或人工决定。T3 Code 对约一半文件跑了两轮，第三票裁决了约 1,900 处分歧。只跑一轮时，高风险区域的删除一律标为争议。
- 鉴权、权限、持久化、迁移相关的删除清单，必须经过人工审阅。
- 顺带记录结构问题，例如一个测试文件覆盖了多个模块，或者测试放错了位置。先在报告中提出调整建议，结构理顺后查重更准。

## 4. 只出报告

报告包括：

- 基线（测试数、墙钟、最慢的文件）；
- 各类别可删、修剪、并入、下沉的数量；
- 按收益排序的文件；
- 预计减少的测试数和耗时（注明是否实测）；
- 需要先完成的前置改动（例如先补齐低层表格，才能删高层）；
- 争议项，以及每项的取舍理由；
- 结构问题；
- 对项目测试文档的补充建议；
- 建议的分批顺序（先做低风险、收益大的）。

报告给用户审阅后，再进入删除。

## 5. 执行删除

- **机械执行**：用语法树按测试名删除（TypeScript 用编译器 API 或 ts-morph，Python 用 libcst，Java 用 JavaParser），不要手工编辑。删除后清掉不再使用的导入、辅助函数和 fixture；空文件整个删除。
- **修剪、并入、下沉**都属于改写，逐个文件手工完成，小批量提交。存在前置改动时，先提交前置改动。
- **后续清理**：
  - 用死代码检查（knip、vulture 等）找出只被已删测试使用的导出：取消导出；没有任何调用方的声明直接删除。确认产品行为不变。
  - 删除孤立的 fixture 和测试数据。
  - 更新引用了已删文件的配置：分片权重、CI 文件清单、空的测试脚本、文档中的链接。
- **刻意保留**的测试列成清单，写明理由。

## 6. 验证

- 类型检查、lint、格式检查、死代码检查全部通过。
- 用第 1 步的命令和机器再跑一次，产出对比表：包、测试数（前 → 后）、墙钟（前 → 后）。
- 剩余的失败与基线对比，相同的标为原有问题。
- **抽查信号**：对保留测试覆盖的几处关键逻辑，以及被删测试声称“已由别处覆盖”的逻辑，各做一次可撤销的故障注入，确认仍然有测试变红。如果没有测试变红，说明删多了，要恢复相应测试。

## 7. 交付

PR/MR 描述包括：

- 为什么清理；
- 评分标准；
- 如何挑选（几轮评审、怎样投票）；
- 前后对比表；
- 刻意保留的清单，以及审阅中恢复的清单；
- 原有的失败。

人工审阅高风险区域的删除清单后再合并。合并后，按 [测试](testing.md#防止回涨) 补上护栏，否则测试会很快涨回来。
