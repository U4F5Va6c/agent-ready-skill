# 文档体系

按读者要解决的问题分层：用户想知道“怎么用”，开发者想知道“为什么这样设计”，维护者想知道“怎么搭建、发布和排障”。每层有自己的写入门槛。门槛比文档数量更重要：多数代码改动不需要改文档，Agent 可以直接读代码。

## 分层

| 目录 | 读者与任务 | 写什么 | 不写什么 |
|---|---|---|---|
| `docs/user/` | 用户完成一项任务、做一个决定 | 每个主要功能一节：做什么、怎么开始、哪里不直观；需要时写设置路径（“设置 → 源代码管理”） | 按钮、图标、布局、动画、每种界面状态；实现细节；贡献者工具 |
| `docs/internals/` | 维护者理解为什么这样设计 | 架构决策及其理由；信任边界；跨组件的约束（包括目录职责与依赖方向）；从源码难以发现的陷阱 | 功能清单；字段、方法列表；常量、超时、迁移编号这类会变的值；控制流叙述；逐个文件的说明；PR 摘要 |
| `docs/operations/` | 维护者执行流程 | 开发环境搭建、发布、排障的步骤和完成标志 | 已安装产品的日常用法（归用户文档） |
| `docs/agents/` | Agent 和 Skills 读取项目绑定 | tracker、triage、domain 等 Skills 需要的配置 | 通用方法（归各 Skill） |
| `docs/adr/` | 回顾某个决定 | 一次决策一篇：背景、选择、后果 | 进行中的讨论 |

规模小的项目可以合并层级，但读者划分不变：一篇文档只服务一类读者。没有外部用户的内部工具，用户层不适用。业务规则、接口契约这类需要实现和评审双方核对的内容，可以单独成层（如 `docs/contracts/`，按主题命名文件）。

## 组织与命名

- **内部文档按代码区域组织。** 一篇对应一块代码区域（如“鉴权与信任边界”“客户端连接”），不要一个功能写一篇。单个功能的讲解，并进所属区域的文档或删掉。T3 Code 在 2026-11 的一次修剪中，把内部文档从 30 篇并成 18 篇，操作手册从 13 篇并成 6 篇，共删掉约 9.7k 行。
- **页数多的层按阅读顺序编号。** 用两位数前缀命名，如 `00_glossary.md`、`01_architecture.md`，术语表和架构概览排在最前。页数少的层不编号。改名时，同步更新所有指向它的链接和评审映射。
- **指令文件里放区域路由表。** 列出“代码区域 → 改动前先读的文档”，并写明评审会按这些文档执行。比起在各处零散地写“参见”，Agent 更容易在动手前找到该读的文档。评审怎样按文档审代码，见 [一份标准，多方读取](feedback-loop.md#一份标准多方读取)。

## 写入门槛

- **内部文档**：动笔前先问，“少了这一段，维护者会具体做错什么？”如果读相关代码就能得到答案，就不写。只和局部有关、代码本身表达不了的原因，写成代码旁的一行注释；需要跨越模块边界或代码装不下的背景，才写内部文档。
- **用户文档**：先问“这段帮用户完成什么任务、做什么决定”。界面上的小调整不写；新增的控件也不必单独成页。
- **新增页面**：要有一个独立、长期成立的理由。现有页面能容纳的，就写成其中一节。

## 维护

- 决策或约束改变时，重写或删除受影响的段落。不要在后面追加“更新：现在改为……”，文档描述的是现状。
- 一条规则只写在一处，其他地方用指针引用，见 [一份标准，多方读取](feedback-loop.md#一份标准多方读取)。
- 链接到源码，不复制源码。字段、数值、命令输出、配置项都会变，复制进文档的内容迟早过期。
- 文档越积越多时，按区域合并，删掉读代码就能得到的内容。
- 链接写相对路径，指向具体章节锚点。

## 索引

`docs/README.md` 是导航入口，按读者分组列出页面：用户指南一组，“参与开发”一组（先指向开发手册和贡献规范，然后是内部文档和操作手册；编号的层按编号顺序列出）。在“参与开发”的开头提醒一句：多数代码改动不需要更新内部文档，新增前先看文档规则。

## 术语表

- 用表格，两列：术语和含义。按领域分组。
- 定义讲清这个词是什么、边界在哪里，并说明它和相邻概念的区别（例如“已接受的命令，不代表其副作用已经完成”）。
- 架构和生命周期约束放进架构概览，不塞进术语定义。
- 一个概念只有一个名字。代码标识符、接口字段和文档用同一个词。
- 创建、补充术语时使用 `domain-modeling`（如已安装）。

## 工作产物

- 实现计划、调研笔记、Agent 草稿不提交；临时材料放在工作区之外。`.plans/` 之类的目录加进 `.gitignore`，只作为兜底。
- 目标架构、重写方案这类设计稿也算计划。落地后，把仍然成立的决策和约束并进区域文档，其余删除，不要在 `docs/` 下长期保留一个专题目录。T3 Code 的那次修剪删掉了约 3.3k 行的 `orchestration-v2/` 设计稿。
- 进行中的工作记录在追踪平台（GitHub Issues、云效 ProjeX 等），合并后的 PR/MR 就是实现记录。工作完成时关闭或更新对应的追踪项，仓库里不保留第二份清单。
- PR/MR 的截图、录屏上传到平台，不提交进仓库。
