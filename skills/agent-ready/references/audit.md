# 审计与接入

逐层检查仓库能为 Agent 提供什么，报告差距，再分批补齐。新仓库与已有仓库走同一流程；新仓库大多数层都是“缺失”，只补当前真正需要的部分。

## 1. 探索

先读，不要假设：

- `git remote -v`：托管平台。云效仓库的追踪与交付交给 `codeup` Skill。
- 根目录的 `AGENTS.md`、`CLAUDE.md`，以及各 harness 的规则目录（`.cursor/rules`、`.claude/`、`.codex/`）；嵌套的指令文件。
- 实际在用哪些 harness：上面的配置目录、提交记录中的 `Co-Authored-By` 等签名、用户的说明。无法确定时问用户，不要猜。
- `README.md`、`CONTRIBUTING.md`、`CODING_STANDARDS.md`、`GLOSSARY.md`、`docs/` 目录树和索引、`docs/agents/`、`docs/adr/`。
- 构建与检查入口：`package.json` scripts、`Makefile`、`justfile`、`pyproject.toml`、`Taskfile`；钩子（`.husky`、`.pre-commit-config.yaml`、`core.hooksPath`）；CI 配置；lint 与类型检查配置。
- 测试目录、测试配置和 fixture 的位置；开发服务器或容器如何启动，状态、端口和 compose 项目名存放在哪里。
- 仓库专属 Skill（`.agents/skills`、`.claude/skills`）、评审机器人配置、MR/PR 模板。
- 敏感数据：真实样本和生产导出的目录只记录路径，不读取内容；`.env` 和凭据文件只看键名（优先看 `.env.example`），不读取值。
- 过去的失误：用 `git log --oneline --grep` 搜索 fix、revert、“误”“冲突”等字样的提交，以及指令文件里已经记下的事故。它们是第 3 步举例的来源。

## 2. 逐层核对

每层给出结论：“已有”“部分”“缺失”或“不适用”，附文件路径或命令输出作为证据。“部分”要写明缺口；“不适用”要写明理由，比如“单端 CLI，没有多客户端”“只用一种 harness”。

参考文件里的做法来自 T3 Code。核对时看仓库有没有起同样作用的规则或机制，不要逐字比对。

| 层 | 检查什么 | 参考 |
|---|---|---|
| 规范源 | 只有一份规范源；实际在用的每个 harness 都能通过导入或软链读到同一份 | [指令文件](instructions.md#一个规范源) |
| 常驻内容 | 每行都通过准入测试；篇幅合理；有冲突时的处理出口 | [准入测试](instructions.md#准入测试) |
| 词汇 | 协作角色与核心领域词已定义；完整词表有固定位置 | [章节骨架](instructions.md#章节骨架)中的“术语”一行 |
| 高危操作 | 会毁数据、伤及正在运行的实例、泄露敏感信息的操作已列出，并给出正确做法 | [章节骨架](instructions.md#章节骨架)中的“高危操作”一行 |
| 改动影响面 | 有项目自己的影响面清单，交付时要说明哪些项适用 | [章节骨架](instructions.md#章节骨架)中的“改动影响面”一行 |
| 文档体系 | 按读者分层；有索引；每层有写入门槛 | [文档体系](docs-system.md) |
| 变更检查 | 一条写进指令文件的命令，覆盖 CI 的快速检查；全量运行超过几分钟时，只检查改动的部分 | [验证与环境](verification.md#一条变更检查命令) |
| 测试规则 | 写明测什么、不测什么、在哪一层测、怎样避免偶发失败 | [验证与环境](verification.md#测试规则) |
| 开发环境 | 一键安装与启动；多工作区互不干扰；有真实形态的测试数据 | [验证与环境](verification.md#开发环境) |
| 护栏 | 有提交前钩子和 CI；绕过检查必须写理由 | [经验回流](feedback-loop.md#机械规则写成检查) |
| 评审标准 | 作者和评审（人或机器人）读同一份标准 | [经验回流](feedback-loop.md#一份标准多方读取) |
| 模型相关文本 | 提示词、工具描述等变更有评测或回放验证 | [经验回流](feedback-loop.md#面向模型的文本按代码对待) |
| 工作产物 | 计划和草稿不入库；追踪平台记录待办，合并后的 PR/MR 记录实现 | [文档体系](docs-system.md#工作产物) |
| Skills 接入 | Matt Skills 的 `## Agent skills` 块与 `docs/agents/` 已就绪；重复出现的多步流程已做成仓库专属 Skill | [指令文件](instructions.md#仓库专属-skill) |

## 3. 报告

先用一张表列出各层，每层一行：层、结论、证据。

再按影响排序，列出最多 6 项改动。先列 Agent 每次都会碰到的问题：读不到规范源、没有验证命令、高危操作没有说明。每项三行：

- **现状**：证据；
- **后果**：不改会导致 Agent 犯什么错，优先举第 1 步找到的真实失误；找不到时写推断，并注明是推断；
- **改法**：最小改动，以及改在哪个文件。

不要把十几层的问题一次全部改完。一批只改一层或一个主题，用户审阅后再改下一批。

## 4. 修改

- 在用户授权的范围内修改，修改前先给出具体 diff。
- 指令文件只有一份可编辑：已有导入机制时，改被导入的那份规范文件。
- `## Agent skills` 块由 `setup-matt-pocock-skills` 管理，原位更新，标题保留英文。项目自己加的内容放在块外，否则重新运行 setup 时可能被覆盖。
- 新增的命令和链接当场验证；写不出可验证内容的章节，不写。

## 5. 复核

修改后由一个没有本次对话上下文的 Agent，只凭仓库文档完成一项小任务。例如：“新增一个接口字段并完成验证”，或“说出改完代码后该运行哪条命令”。凡是它答错或卡住的地方，就是指针或文档还缺的部分。
