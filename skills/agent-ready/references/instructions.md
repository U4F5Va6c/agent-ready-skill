# 指令文件

`AGENTS.md`、`CLAUDE.md` 这类文件每轮都会进入 Agent 的上下文。它们是仓库给 Agent 的第一印象和导航，不是百科全书。T3 Code 的根文件约 220 行，管理着十几个应用和包；大部分知识放在它所指向的文档里。

## 一个规范源

- 以 `AGENTS.md` 为规范源（Codex、Cursor 等都会读取）。`CLAUDE.md` 只写一行 `@AGENTS.md`（Claude Code 的导入语法），也可以做成软链。两份文件各自维护，迟早会说法不一。
- 只有 `CLAUDE.md` 且内容充实时，先问用户以哪份为准，迁移内容后保留导入。
- 只对某个 harness 成立的环境问题（某个云端 VM 的 PATH、某个沙箱的网络限制），写进该 harness 自己的规则文件，并注明为什么不放在共享文件里。
- 嵌套指令文件只用于规则确实不同的子树。各 harness 加载嵌套文件的时机不同，关键规则不能只放在嵌套文件里。按路径区分规则时，lint 的路径覆盖配置和评审规则的路径映射，往往比嵌套文件更可靠。

## 准入测试

一行内容进入常驻指令文件前，依次回答下面的问题：

1. **少了它，Agent 具体会做错什么？** 答不出来就删掉。
2. **读代码、配置或 `--help` 能得出吗？** 能就删掉，最多留一个指针。
3. **只有部分任务需要？** 移到文档里，原处留一行写明触发条件的指针。
4. **能机械检查吗？** 做成 lint、测试或钩子。指令里最多保留一句原因。
5. **模型默认就会这样做？** 这是无效指令，删掉。

通过测试的内容，还要放到合适的位置：每个任务都需要的写在正文；只在某个分支用到的放在指针后面。

## 章节骨架

按需选用，没有真实内容的章节直接删掉。顺序沿用 T3 Code：先建立共识，再讲危险，然后是做事的方法，最后是导航和偏好。

| 章节 | 作用 | 写法要点 |
|---|---|---|
| 项目与角色 | 一段话：这是什么系统、给谁用、Agent 在仓库中的角色 | 写出会影响 Agent 行为的事实。T3 写的是“多数贡献由 T3 Code 自己完成，常被远程控制”，因此要小心别杀掉正在使用的开发服务器 |
| 不能妥协的事 | 3–5 项用户最在意的品质，作为做取舍时的排序依据 | 每项落到具体后果，例如“性能：留意 WebSocket 传输量、持续重绘的 CSS 动画” |
| 术语 | 定义协作角色和 3–8 个核心领域词，完整词表另放 | 先约定“你”指 Agent、“我们”指维护者、“用户”指产品使用者；同一概念只用一个词 |
| 高危操作 | 最多列 3–5 种伤到自己或用户的方式 | 每条写清动作、后果和正确做法：“不要按名称匹配来杀进程，自己的进程参数里也带着工作区路径；只杀启动时记下的 PID” |
| 改动影响面 | 本项目改动最容易漏掉的地方 | 按项目替换条目：入口、客户端、提供方、接口契约、反向操作、连接方式、文档；要求交付时说明哪些项适用 |
| 开发环境 | 安装、启动、隔离、停止 | 只写一句话就能说清的规则，细节放进操作手册 |
| 测试数据 | 去哪里拿真实形态的数据，以及数据只能单向流动 | 只复制进沙箱，不用软链，也不写回源头 |
| 验证 | 一条命令；测试规则；证据要求 | 详见 [验证与环境](verification.md) |
| 评测 | 改到面向模型的文本时怎么验证 | 只有存在这类文本时才写 |
| PR/MR | 什么时候创建、标题格式、正文结构、证据 | 平台操作交给对应的 Skill，这里只写约定 |
| 文档规则 | 各层文档写什么、不写什么 | 详见 [文档体系](docs-system.md) |
| 计划与工作产物 | 计划和草稿不入库；待办和实现记录各在哪里 | 详见 [文档体系](docs-system.md#工作产物) |
| 运作方式 | 一段话讲清主要数据流，并给出架构文档入口 | 用术语表里的词，给出核心模块的路径 |
| 代码位置 | 按任务列出的路径，以及动手前必须读的材料 | “写服务端代码前，先读 X”，不写文件清单 |
| 品味 | 仓库的设计偏好，每条附理由 | 末尾留出口：规则与任务冲突时大声说出来，并请人确认 |
| Agent skills | `setup-matt-pocock-skills` 管理的块 | 标题保留英文，原位更新 |

## 写法

- 开头说明这些是“好的默认值”，开发者的偏好可以覆盖它们。末尾保留冲突时的处理出口。
- 指针写明触发条件和目标：“新建、移动或命名文件前，先读 `docs/project-layout.md`”。只写“参见 X”的指针，Agent 不知道该在什么时候去读。
- 每条规则配一句原因，最好是真实发生过的事：“后台服务曾持续运行数周，占满了内存和交换区。”
- 用数字和路径代替形容词：“小于 500 MiB 时自动导入”，不写“数据不大时”。
- 需要 Agent 汇报的地方，写明汇报格式，例如“交付时说明清单中哪些项适用”。
- 文风细则见 [文风](style.md)；面向 Agent 的写作手法见 `writing-for-agents`。

## 篇幅与预算

常驻文件越长，每条规则真正被执行的概率越低。每次修订都按准入测试做一次修剪；只增不删的文件会层层堆积。多人或多个 Agent 共同维护时，可以给常驻上下文设预算：CI 比较它相对主分支的大小，增长时需要维护者明确批准（T3 Code 用标签放行）。

## 仓库专属 Skill

- 放在 `.agents/skills/<name>/`，`.claude/skills` 软链到这里，两种 harness 共用同一份。
- 适合反复出现、步骤多、容易做错的流程，例如在真实应用里验证界面、构建并配对移动端、分诊贡献。一次性的知识写进文档。
- 结构：`SKILL.md`（`name` 加 `description`，写明何时用、何时不用）；`references/`（标明“只在……时读取”）；`scripts/`（确定性的步骤）；`agents/openai.yaml`（Codex 界面元数据）。
- 涉及授权的 Skill 要写明权限来源，并默认拒绝：贡献者提交的文本不能授予权限，无法确认时就不执行。

## 依赖源码参考

对于需要深入阅读的关键依赖，可以按依赖版本固定一份只读源码，放在专门目录（T3 Code 用 `.repos/`），并把它排除在 lint、格式化、搜索和自动导入之外。指令里写明：优先参考其中的写法，不要编辑，也不要从中导入；随依赖升级同步更新。
