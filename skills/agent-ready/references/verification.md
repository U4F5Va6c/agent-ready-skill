# 验证与环境

Agent 能不能交付可信的结果，取决于仓库能不能让它低成本地证明自己是对的。验证命令、测试规则和开发环境都是给 Agent 用的工具，和代码一样需要维护。

## 一条变更检查命令

提供一条命令，在推送前跑完 CI 中的快速检查，并且只针对改动的部分。T3 Code 的 `check:changed` 是这样做的：

- 以最近的远端主分支为基准，加上未提交和未跟踪的文件，确定改动范围。
- 对改动的文件做格式检查和 lint；对受影响的包及其下游做类型检查；只跑改动文件旁边的测试（`foo.ts` 对应 `foo.*.test.*`）。不用依赖图去推导相关测试：一个底层文件曾因此牵出四百多个测试文件中的两百五十多个。
- 判断“哪些检查需要跑”时，和 CI 复用同一段代码，避免本地和 CI 的判断不一致。
- 按 CPU 核数和内存限制并行；超时的步骤连同其进程组一起结束，并报告为超时，不能静默挂起。
- 按输入的哈希缓存结果：文件没变时再次运行，直接给出上次的通过结论。

小项目不需要做得这么复杂。全量快检几分钟内就能跑完时，一个 `make check` 目标串起 lint、类型检查、快速测试就够了；超过几分钟，再按 `git diff --name-only` 的结果裁剪范围。关键是命令只有一条、写进指令文件，而且 Agent 真的会去运行它。

指令文件还要写明不该跑什么：“不要运行全仓库检查，那是 CI 的事。”否则 Agent 会为了保险，每次都跑一遍全量测试。

## 测试规则

写什么、不写什么、在哪一层写、怎样保持确定性，见 [测试](testing.md)。

## 交付证据

- 交付说明不能只写“测试通过”，要写针对本次改动做了哪些测试或手工检查、观察到什么结果，以及哪些没有检查。
- 可以重放的缺陷，最好提供“基准版本失败、修复版本通过”的对照证明。T3 Code 的 `scenarios:prove` 会在两个临时工作区里分别运行同一场景；退出码区分“已证明”“运行了但没有证明”“应用起不来”“场景本身坏了”。
- 截图、录屏上传到评审平台，不要提交进仓库。

## 开发环境

- **一键安装**。在新建工作区时，自动安装和初始化脚本标记进度：运行中（文件内写 PID）、完成、失败（附最后若干行输出）。用信号处理保证一定会写下结束标记，这样 Agent 能等待安装完成，而不会和安装过程抢跑。
- **工作区隔离**：每个工作区（worktree）用自己的状态目录、数据库和端口。端口从工作区路径的哈希推导，重启后保持稳定。显式参数的优先级最高。用容器开发时，compose 项目名、卷和端口也要按工作区区分；否则在新工作区启动，会接管或删除主工作区正在运行的容器。工作区里缺少隔离配置时，启动命令应该直接报错，而不是悄悄套用默认值。
- **保护真实环境**：开发服务器默认不连接开发者正在使用的真实数据；需要真实形态的数据时，从只读快照复制进工作区，并剔除凭据、定时任务和外部连接。
- **资源上限**：开发服务器超过内存上限时自行退出，退出信息里说明怎样调整上限。不要用 `nohup`、`setsid`、`tmux` 让服务脱离会话运行；带 `restart` 策略的后台容器同理，会话结束时要停掉自己启动的容器。
- **停止**：只停止自己启动的进程，按启动时记下的 PID 停止。
- **省钱的替身**：如果需要调用付费的外部服务（模型、短信、支付），提供一个免费的回放或模拟实现，并在指令里写明默认用它，只在必要时选最便宜的真实档位。

## 端到端验证

用户可见的改动，在集成后由主 Agent 在真实客户端里完整走一遍。子 Agent 不各自启动开发服务器。这个流程如果反复出现，就做成仓库专属 Skill（见 [指令文件](instructions.md#仓库专属-skill)）。
