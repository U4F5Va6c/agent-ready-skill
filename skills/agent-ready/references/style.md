# 文风

人和 Agent 都会读仓库里的文字：指令、文档、注释、lint 报错、提交和 MR 描述。好的文风让读者用最少的注意力做对事情。下面的规则来自对 T3 Code 文档的拆解，用中文写作时同样适用。

## 句子层面

- **先给结论或规则，再给原因。** 第一句就能用上：“Portable handoffs are textual summaries. They do not claim native provider context parity.” 不要从背景铺垫起。
- **规则配原因，原因用真事。** “不要用 `nohup` 把开发服务器挂到后台。这类进程曾运行数周，占满内存和交换区。”有了原因，Agent 才能在规则没覆盖的情况下做出相近的判断。
- **禁令配正确做法。** “不要按名称匹配来杀进程；只杀启动时记下的 PID。”只写禁令会让被禁止的动作更显眼，读者也不知道该怎么做。
- **具体代替形容。** 写“至多 16 GiB”“每 2 核一个并行步骤”“截断到 240 字符，保留前 237 个字符加 `...`”，不写“合理的上限”“适当并行”。
- **主语清楚，动词具体。** 少用“进行”“实现”“相关”“处理”这类空泛动词，以及“一些”“部分”“等等”。“系统会对数据进行相关处理”要改成“服务端把每段连续空白合并为一个空格”。
- **划清容易误读的边界。** 在读者可能混淆的地方写明“不是什么”：“不要把迁移时的 32,000 字符预算说成交接的上限。”
- **一个概念一个词。** 用术语表里的词，不为了避免重复而换同义词。同一篇里先写“线程”、后写“会话”，读者会以为是两样东西。
- **不加修饰和铺垫。** 删掉“值得注意的是”“众所周知”“为了更好地”“本文将介绍”。删掉它们，意思不受影响。

## 结构层面

- **列表项用粗体引导词开头。** 例如“**入口**：从聊天视图能触发的行为，通常也能从设置、命令面板和快捷键触发。”读者扫一眼引导词就知道这一项讲什么。
- **完成标准可以检查。** 写“交付时说明清单中哪些项适用”，而不是“确保考虑周全”。
- **默认值配出口。** 写明“这些是好的默认值，开发者偏好可以覆盖”，以及“规则与任务冲突时大声说出来，并请人确认”。
- **按读者分开写。** 用户文档用产品的口吻，说用户做什么、在哪里设置，用平台限定词说明适用范围（“在网页和桌面端……”）。内部文档用代码符号名，讲约束和理由。操作手册写成可以复制的命令，加上完成标志。
- **只写现状。** 改动后重写原段落，不留“更新于……”“原来是……”这样的历史层。

## 代码注释

- 默认不写注释。只写代码表达不了的东西：约束、外部系统的怪异行为、不变量。尽量一行，最多四行。
- 不复述名称和签名，不逐步讲解代码，不记录改动历史，不解释刚做的修复；这些内容放在 PR 里。
- 抄近路的地方写明它的局限，以及什么时候需要升级。
- 能机械识别的低价值注释（分隔线、只有准备、执行、断言之类步骤名的测试注释、没有链接的 TODO、被注释掉的代码），交给 lint 拦截。

## 报错与 lint 消息

Agent 会读这些消息并照着做，所以把它们当指令来写：

1. 用一句话说明哪里不对、为什么不对；
2. 依次列出正确的替代做法；
3. 最后才给“确实需要时”的出口，并要求写出理由（`-- reason`）；
4. 堵住投机取巧的改法：“把同样的逻辑挪进 ref 或 store 来躲开这条规则，不算修复。”

## 面向模型的文本

提示词、工具描述、Skill 和指令文件都是代码：修改要经过评审，能评测的就评测。写法见 `writing-for-agents`（如已安装），要点如下：

- 指针写明触发条件；一个分支只用一个触发词。
- 每个常驻的字都有成本；删掉模型默认就会做到的指令。
- 用模型本来就熟悉的引导词，代替一整句解释。

## 中文写作

- 短句。一句话只讲一件事，长句拆开写。
- 代码符号、命令、路径、配置键保持原文，用反引号包起来；产品界面文字用 **粗体**，和界面上显示的完全一致。
- 术语第一次出现时可以附英文原文，之后统一使用同一个写法。
- 避免翻译腔：少用“被”字句和“对……进行……”；“该”“此”不要连用。
- 标点和中英文间距沿用项目现有文档的写法；没有先例时，正文用全角标点。
